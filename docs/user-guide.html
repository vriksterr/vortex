Vortex User Guide

A small, fast, encrypted multipath UDP tunnel. This guide explains how it is built, how to deploy it, what every command does and what its output looks like, and how to pick settings that suit your network.

Applies to the fork documented in this repository (reports vortex 1.0). Commands and flags were checked against the source code.

About the example output

Output layouts shown here come directly from the program's print statements. The numbers in them (addresses, speeds, PIDs, round-trip times) are illustrative — yours will differ. Lines beginning with $ or # are commands you type; # means "as root".

1. Overview

Vortex creates a virtual network interface (a TUN device) on two machines. Anything you send into that interface on one machine comes out of the same-named interface on the other, encrypted and authenticated in transit. Between the two machines it travels as UDP datagrams, and it can use several network links at once — for example a fibre line, a DSL line and an LTE modem — so a single connection can use their combined bandwidth and survive any one of them failing.

Multipath

Packets are spread across all healthy links in proportion to each link's capacity. A dead link is dropped automatically and re-added when it recovers.

Failover & backup

Mark links as primary or backup with pref. Backups carry traffic only when nothing preferred is working.

Secure by default

AEGIS-256 (or ChaCha20-Poly1305 fallback), Curve25519 key exchange with perfect forward secrecy, hourly key rotation, timestamp checks.

Multi-core

Several worker threads run the whole packet pipeline in parallel; a multi-queue TUN spreads the load further on Linux.

Sub-flows

Split one link into N parallel UDP flows (connections N) to fill long, high-latency pipes.

Many clients

One server can serve many clients on one port, each with its own key and its own limits, completely isolated from the rest (chapter 6).

Operator-controlled

Fixed MTU, rate limits and loss/RTT limits are explicit settings — no hidden probing that can mislead you.

What Vortex is and is not

  • It is a layer-3 tunnel between a client and a server, secured by a pre-shared key. A server can also serve many independent clients at once, each with its own key and its own limits (see chapter 6); one client talks to exactly one server.
  • It is not a mesh VPN, does not hand out IP addresses, set up routes, or configure NAT or firewalls. You assign addresses and routes with ordinary tools (ip, systemd-networkd, …).
  • It has no configuration file. Everything is given on the command line when you start it, and changed at run time with set and path. Wrapper scripts or systemd units make it permanent.
  • Linux is the primary platform. macOS and the BSDs are supported for the core tunnel; interface tracking (via), multi-queue TUN, cpus and the systemd files are Linux-only.

Roles: server and client

The two ends are symmetric once connected, but they behave differently at start-up:

  • The server (passive side) simply listens on a UDP port. It does not need to know the client's addresses; it discovers every path the client uses by looking at where valid packets come from.
  • The client (active side) is told where the server is (to addr… port…) and which local links to use (path up via…). It starts the conversation.

Per-path health, rate and MTU settings configured on the client are carried to the server inside the encrypted control messages, so the server normally needs no per-path configuration at all.

2. How it works

2.1 The journey of a packet

Sending side:

  1. An application sends a packet to an address routed into the TUN device. A worker thread reads it from the TUN.
  2. If the tunnel's rate allowance is exhausted, the worker sleeps 1 ms and tries again (back-pressure instead of burning CPU).
  3. The packet is encrypted and authenticated. A 6-byte timestamp (also used as the cipher nonce) goes in front and a 16-byte authentication tag is added.
  4. A path is chosen for that individual packet by a weighted random pick (see paths & scheduling).
  5. The datagram is sent from the chosen local socket, with the chosen source address and interface pinned using packet-info control data.

Receiving side:

  1. A datagram arrives on one of the UDP sockets. Packets are pulled in batches of up to 16.
  2. Its timestamp is checked against the local clock (default tolerance: 10 minutes). Outside the window it is dropped and counted as a clocksync error.
  3. It is decrypted. If authentication fails it is dropped and counted as a decrypt error.
  4. The path it arrived on is looked up (or created automatically on a passive peer).
  5. Control messages are processed internally. Data packets are checked to be well-formed IPv4/IPv6 (version and length fields must match the size received) and written to the TUN device, where the kernel takes over.

2.2 Cryptography and key management

2.3 Paths and scheduling

A path is one (local interface/address, remote address, local socket) combination. Paths are created in two ways:

  • Active: by you, with vortex path up… (usually on the client).
  • Passive: automatically, the first time a valid packet arrives from a new source. This is how the server learns the client's links. Passive paths that stay silent for 5 minutes are removed.

Each path goes through states you will see in vortex path: probing → running (or ready for a backup), and drops to degraded, lossy, late or waiting when something is wrong (see section 10).

Scheduling is per packet, not per connection. For each outgoing packet a pseudo-random number (taken from the encrypted bytes) is mapped over the weights of all running data paths, so traffic splits roughly in proportion to each link's rate. The weight of a path is the average rate of all sub-flows on the same physical link, so every sub-flow of a link gets an equal share while different links share by capacity.

Preference. Every path has pref (0–127, lower is better). Only paths at the best preference level that currently has a working path carry traffic; worse ones sit in ready as warm standby and take over as soon as no better path is running.

2.4 Sockets and sub-flows (connections N)

One TCP connection over one UDP flow is often limited by a single link's bandwidth-delay product, and many carriers and kernels treat a single flow as one unit (one hash bucket, one CPU core). connections N opens N UDP sockets with different source ports on the same interface and treats each as a sub-flow of the same link. They are load-balanced evenly, which helps fill long, fat links and spreads receive work across CPU cores. The peer needs no setting: it just sees N more source ports.

Internally the program also keeps a pool of sockets that all listen on the same port (kernel SO_REUSEPORT), so a server with many incoming flows spreads receive work across its workers. Once a passive path proves it is alive it is moved to its own connected socket. This is why the socket numbers shown by vortex path start well above 0 (see section 10).

2.5 Health monitoring and failover

Detecting a link that is up but dropping packets needs measurement that does not depend on how much data happens to be flowing. Vortex uses a dedicated monitor sub-flow per physical link:

  • It carries no user data. It sends a tiny, sequence-numbered probe at a fixed interval (default 1 second).
  • The receiver counts missing sequence numbers over the last probewindow probes (default 60) — that is the loss percentage.
  • Each probe also reports the sender's own view of what it receives. This matters: whether to keep sending on a link depends on whether the peer hears you, so the decision to mark a link lossy is made from the peer's report of loss in your sending direction.
  • Degradation is fast (the moment loss exceeds losslimit); recovery is slow (loss must stay below the limit for proberecover, default 60 seconds) to stop flapping.
  • If a monitor hears nothing for a whole window, the link is treated as 100% lossy.
  • Settings given on the client (probeinterval, probewindow, proberecover, losslimit, rttlimit) are propagated to the server automatically.
Add monitor on every link

Without a monitor, loss-based failover cannot trigger: losslimit has nothing to measure and vortex path shows probe-status no-monitor. Links are still marked degraded when the peer stops answering altogether, and late when RTT exceeds rttlimit, but a link that merely drops a fraction of packets will keep being used.

2.6 Rate control and shaping

Each path has a transmit rate that the scheduler uses as its weight and that also limits how fast the tunnel as a whole may send (a token-bucket window refilled at the sum of running rates, capped to about 100 ms of data).

  • rate fixed tx X — use exactly X as the ceiling. Predictable; recommended when you know your line speed.
  • rate auto (default) — start at about 1 Mbit/s and grow by roughly 10% per measurement while the path is not congested, backing off to ~7/8 of the rate the peer actually observes when it is. A tx value, if given, is the upper cap. Marked experimental.
  • rx X is sent to the peer: it tells the other side how fast it may send to you. So you limit your inbound traffic by setting rx on your own side, and your outbound with tx.
  • An explicitly set tx is pinned: the peer's advertisements can no longer overwrite it.

Rates are stored as bytes per second. You can write them in bits or bytes with suffixes (see path). Good shaping (setting rates a little below real capacity) keeps queues, and therefore latency, small.

2.7 MTU

There is no MTU discovery. Each path sends datagrams of one fixed size — its mtu setting (default 1400 bytes of UDP payload) — and never changes it automatically. If you set mtu on one end, it is advertised and adopted by a peer path that has none of its own.

  • The tunnel interface MTU is automatically set to the smallest path MTU of any up path, minus 22 bytes (6 timestamp + 16 tag). The default is therefore 1378.
  • The outer packet on the wire is mtu + 8 (UDP) + 20 (IPv4) or 40 (IPv6). With 1400 that is 1428 / 1448 bytes, safe for 1500-byte Ethernet and for PPPoE (1492).
  • If your underlying links are plain Ethernet you may raise mtu to at most 1472 (IPv4) or 1452 (IPv6) to save overhead.
  • When packet resequencing is active (reorderwindow set and strictorder on, the default), every data packet, TCP included, carries 4 extra encrypted bytes; leave a little headroom if you push the MTU to the limit.

2.8 Packet reordering (optional)

Because packets of one flow are sprayed over links with different latency, they may arrive out of order. TCP interprets reordering as loss, retransmits and slows down, so a single download can be much slower than the sum of the links. Two settings control a resequencing buffer on the receiving side (vortex set):

  • reorderwindow DURATION (off by default) switches resequencing on and sets the longest wait for a missing packet.
  • strictorder on|off (on by default) chooses how packets are put back in order. It only has an effect while a reorderwindow is set.

With strictorder on:

  • The sender numbers every data packet (4 extra encrypted bytes), TCP included, and the receiver releases packets strictly in number order, waiting only for a number that is genuinely missing, for no longer than the window. An in-order packet is never delayed.
  • A packet that is really lost holds back what follows it for a short time (the arriving path's delay difference plus about 3 ms, never more than the window); then the rest is released together.
  • The receiver asks for the numbers, so each direction is set on the machine that receives it — set both ends to resequence both ways. Whether TCP is numbered is agreed through the control messages, so an older build on the other end simply keeps getting the old behaviour (nothing breaks).

With strictorder off the older method is used: only non-TCP traffic is numbered, and TCP is held for a time derived from the measured RTT difference between the arriving path and the slowest path. That estimate is not precise enough to restore exact order at high packet rates, which is why strict order is the default.

Either way it never drops packets; if the buffer is full or a packet is too large, it is delivered immediately. See section 7 for sizing.

2.9 Threads, interface tracking and the control plane

  • Workers. By default cores − 1 threads (at least 1, at most 32), each running the entire pipeline with no hand-offs. Override with bind workers N or confine to specific cores with bind cpus.
  • Locks. Two short-held mutexes protect shared state; neither is held during a system call or while encrypting, so crypto runs fully in parallel.
  • Housekeeping thread. About ten times a second: timers, keepalives, key rotation, health, rate and MTU updates. It also serves control requests.
  • Interface tracking (Linux). Paths created with via INTERFACE remember the interface name. A netlink subscription notices link up/down and address changes. If the link goes down the path is suspended; when it returns (even with a new IP, such as an LTE modem reconnecting) the path is re-bound automatically and re-measured. Your configuration is kept.
  • Control socket. A Unix datagram socket named after the TUN device, in a per-user runtime directory (mode 0700). The CLI commands connect to it, so run management commands as the same user that started the tunnel (normally sudo). The directory is the first usable of /run/user/<uid>/vortex, /run/vortex.<uid>, /var/run/vortex.<uid>, /tmp/vortex.<uid>.

3. Install

Requirements

  • A C compiler and make (or Meson + Ninja), and git.
  • Nothing else. The cryptography library (libsodium 1.0.22) is included in the project and built for you.
  • Linux with TUN support (/dev/net/tun) and root or CAP_NET_ADMIN to run a tunnel. Building, keygen, version and bench need no privileges.
  • Accurate clocks on both machines.

Build

$ git clone --recurse-submodules  vortex
$ cd vortex
# already cloned without submodules?
$ git submodule update --init --recursive
$ make                         # builds the bundled libsodium once (~25 s), then vortex
$ sudo make install            # installs ONE self-contained executable to /usr/local/bin

The first make builds the bundled libsodium privately into .sodium/ (no network access, nothing installed on the system) and links it statically into vortex, so the installed program does not depend on any libsodium package. Later builds reuse it. make distclean removes it again. To install somewhere else: make install PREFIX=/opt/vortex.

$ make SODIUM=system
$ meson setup build
$ meson compile -C build
$ sudo meson install -C build        # also installs the systemd files
# -Dbundled_libsodium=enabled always uses the bundled copy; =disabled requires a system one
$ make X=aarch64-linux-gnu-      # builds libsodium and vortex with that toolchain
$ ./vortex version
vortex 1.0
libsodium 26.4

The second line is the version of the libsodium built into the program (26.4 is the library version number of the bundled libsodium 1.0.22).

4. Quick start: two machines in ten minutes

Scenario: a server with public address 203.0.113.10 and a client behind a normal connection on interface eth0. The tunnel uses the private network 10.77.0.0/30, UDP port 5000, and device name vx0 on both ends.

Step 1 — Create the shared key (once)

$ install -d -m 700 secrets
$ ./vortex keygen > secrets/vortex.key
$ chmod 600 secrets/vortex.key
$ cat secrets/vortex.key
9F3A61C0D2B84E57A1F0C3D9E6B2748A5D01CE93F7B6A42E8D5C1B0A3F7E9D62

Copy the same file to the other machine over a secure channel (e.g. scp). Never post it or commit it to version control.

Step 2 — Start the server

Open UDP port 5000 in the server's firewall first.

# ./vortex bind dev vx0 keyfile secrets/vortex.key from addr 0.0.0.0 port 5000
running on device vx0 as pid 2417

This command stays in the foreground and prints log messages to the terminal. Use another terminal for the next steps (or run it under systemd, see section 8).

Step 3 — Give the server's tunnel interface an address

# ip address add 10.77.0.1/30 dev vx0
# ip link set vx0 up

Step 4 — Start the client

# ./vortex bind dev vx0 keyfile secrets/vortex.key \
      from addr 0.0.0.0 port 0 \
      to addr 203.0.113.10 port 5000
running on device vx0 as pid 981

Local port 0 lets the operating system choose a free port.

Step 5 — Address the client's interface and add its link

# ip address add 10.77.0.2/30 dev vx0
# ip link set vx0 up

# Tell vortex which local link to use, and cap it (see section 7 for how to pick values)
# ./vortex path up via eth0 dev vx0 monitor rate fixed tx 50mbit rx 100mbit
path dev vx0 via eth0 to addr 203.0.113.10 port 5000 set up pref 0 beat 100ms losslimit 100% rttlimit off mtu 0 rate fixed tx 50Mbits rx 100Mbits  monitor

The command prints the configuration it applied. mtu 0 means "use the default (1400)".

Step 6 — Check that it works

# ./vortex path dev vx0
eth0  index 2  192.168.1.20 -> 203.0.113.10:5000  rtt 18.402  tx -  rx -  recv-loss 0.00  peer-loss 0.00  probe-status healthy
  ├─ 16  running   monitor  tx -  rx -  rtt 18.402  mtu 1400  public 198.51.100.7:41873
  └─ 17  running   tx -  rx -  rtt 18.311  mtu 1400  public 198.51.100.7:48155

# ping -c 3 10.77.0.1
64 bytes from 10.77.0.1: icmp_seq=1 ttl=64 time=19.2 ms
64 bytes from 10.77.0.1: icmp_seq=2 ttl=64 time=18.7 ms
64 bytes from 10.77.0.1: icmp_seq=3 ttl=64 time=18.9 ms

If both rows say running and ping works, you have a tunnel. If not, see Troubleshooting.

Step 7 — Send real traffic through it

Vortex only provides the pipe. To use it as an Internet gateway for the client, the server needs IP forwarding and NAT, and the client needs a default route through 10.77.0.1 plus a host route that keeps the packets to 203.0.113.10 going out of eth0 (otherwise the tunnel's own packets would loop into the tunnel). A typical set:

# sysctl -w net.ipv4.ip_forward=1
# iptables -t nat -A POSTROUTING -s 10.77.0.0/30 -o eth0 -j MASQUERADE
# keep the path to the server outside the tunnel (use your real gateway)
# ip route add 203.0.113.10/32 via 192.168.1.1 dev eth0
# send everything else through the tunnel
# ip route add 0.0.0.0/1 via 10.77.0.1
# ip route add 128.0.0.0/1 via 10.77.0.1

Using two /1 routes overrides the default route without deleting it, so removing them restores normal connectivity instantly.

Step 8 — Stop

Press Ctrl-C (or send SIGTERM) in the terminal running bind. The TUN interface disappears unless you started with persist.

5. Command reference

The program is one binary with nine commands. Running vortex with no arguments lists them:

$ vortex

  list                       List all tunnels
  show                       Show tunnel information
  bench                      Start a crypto bench
  bench multicore            Bench aggregate multi-core crypto throughput
  bench multicore fallback   Same, using the ChaCha20 fallback cipher
  bind                       Start a new tunnel
  bind qlen                  Set the tun device's tx queue length, ...
  bind workers               Number of worker threads, ...
  bind cpus                  Only use these CPU cores, ...
  bind hub                   Serve many independent clients (see chapter 6)
  set                        Change tunnel properties
  keygen                     Generate a new secret key
  path                       Manage paths
  path watch                 Live-refresh path status every second
  path mtu                   Set the fixed MTU to use, ...
  path connections           Parallel UDP sub-flows for one path, ...
  peer                       Manage clients of a multi-client tunnel
  version                    Show version

Syntax conventions

  • Arguments are bare words, not --flags: vortex show dev vx0, never --dev vx0.
  • help can be appended almost anywhere to list the options valid at that point: vortex path help, vortex bind help.
  • Addresses are written with explicit keywords: addr 203.0.113.10 port 5000. IPv4 and IPv6 are both accepted (addr 2001:db8::1).
  • dev NAME selects which tunnel a management command applies to. You can omit it if exactly one tunnel is running; with several you must give it. vortex list shows the available names.
  • Durations accept ms, s, m, h, d, w (250ms, 30s, 2h). A bare number means seconds for options such as kxtimeout or keepalive, so write 100ms explicitly for milliseconds.
  • Rates are bytes per second. Suffixes: b/bit/bits = bits; B/byte/bytes or none = bytes; prefixes k, m, g (decimal) or with i (kib, binary). So 10mbit = 10 Mbit/s = 1,250,000 B/s, 10MB = 10,000,000 B/s, and a plain 12500000 = 12,500,000 B/s = 100 Mbit/s. Things like mbps are not accepted.
  • Options that cannot be used together (for example via and addr) produce Option X is not compatible with Y.

5.2 bind — start a tunnel

vortex bind keyfile FILE
    [dev NAME]
    [from addr LOCAL_IP port LOCAL_PORT]
    [to   addr REMOTE_IP port REMOTE_PORT]
    [persist] [chacha] [qlen N] [workers N] [cpus LIST]

Creates the TUN interface and the UDP sockets, starts the worker threads and the control socket, then stays in the foreground until stopped. It does not assign an IP address or bring the interface up; you do that with ip. It does set the interface MTU automatically (see MTU).

keyfile FILE required
File whose first 64 characters are the hex key from keygen. Trailing newline is fine. Error if missing: a keyfile is needed!.
dev NAME
Name of the TUN interface to create or attach to (vx0). If omitted, Linux tries tun0 through tun31 and uses the first free one. On macOS the name must look like utun3.
from addr IP port PORT
Local address and UDP port to bind. Default 0.0.0.0 port 5000. Use port 0 on a client for an automatic port. Use addr :: for IPv6 (on Linux this also accepts IPv4 on the same socket). Binding a specific address restricts which local address is used; 0.0.0.0 is normal for a multi-link client because path up via selects the link.
to addr IP port PORT
The remote endpoint (the server's address). Give it on the client. Leave it out on a pure server. It is also the default remote for later path up commands. Default 0.0.0.0:5000 (meaning "none").
persist
Keep the TUN interface (and its addresses/routes) alive after the process exits, so a restart does not disturb other software. Without it the interface is removed on exit. A SIGHUP also requests persistence before stopping.
chacha
Force ChaCha20-Poly1305 instead of AEGIS-256. Useful when one side has no AES hardware, or for testing. If AES is unavailable anyway the program prints AES is not available, enjoy ChaCha20! and falls back by itself.
qlen N
Set the TUN device's transmit queue length (packets). Larger values absorb bursts at the cost of more potential delay. Leave unset for the kernel default.
workers N
Number of worker threads (1–4096 accepted, effectively limited to 64 and 4× your core count). Default: cores minus one. More workers than cores can help spread many sub-flows evenly, but costs context switches. See section 7.
cpus LIST
Linux only. Confine the whole process to the listed cores, e.g. 0-2 or 0,2,4-5. Every core must be currently available to the process or the command fails. If workers is not set, one worker per listed core is used. Useful to keep vortex away from cores busy with something else.

Multi-client servers add three options — hub, peers FILE and mtu N — and use no keyfile; see chapter 6.

5.5 set — tunnel-wide settings

vortex set [dev NAME]
    [kxtimeout DURATION] [timetolerance DURATION]
    [keepalive DURATION] [reorderwindow DURATION] [strictorder on|off]

Changes settings of the running tunnel immediately and prints the resulting values. Run with no options to just display the current values. Settings are not saved; re-apply them at start-up (see section 8).

OptionDefaultWhat it does
kxtimeout1hHow often session keys are rotated. Shorter rotates more often (more forward secrecy, negligible cost); the two peers do not need to match.
timetolerance10mMaximum difference accepted between a packet's timestamp and the local clock. Smaller is stricter against replay but needs well-synced clocks.
keepalive25sInterval of idle keepalive messages on an otherwise quiet single-socket path. Keep below NAT/firewall UDP timeouts (often 30–60 s).

Per-sub-flow settings

Rate, preference and the other settings are applied to each sub-flow. With connections 4 and rate fixed tx 50mbit every sub-flow is capped at 50 Mbit/s, so the link as a whole may use up to 4× that. Divide your line speed by the number of sub-flows when you size the cap.

Options in detail

up / down
up enables (and creates) a path; down disables it, including all its sub-flows and monitor. A path must be created with up first. The desired state is remembered: if the interface disappears the path is suspended and returns on its own.
rate [fixed|auto] [tx RATE] [rx RATE]
tx: maximum sending rate on this path (pinned, cannot be changed by the peer). rx: maximum rate you allow the peer to send to you on this path (advertised to the peer). fixed: use these exactly; auto: adapt dynamically (default; experimental). With fixed, always give tx, otherwise the rate stays at its small starting value (about 1 Mbit/s). Examples: tx 50mbit, rx 12500000 (bytes/s), tx 5MB.
pref N
Preference 0–127, lower is better, default 0. Paths with a higher number carry traffic only when no lower-numbered path is working (ready = standby). Equal values load-share.
connections N
Number of parallel UDP sub-flows (1–4096; stay at or below about 32). Default 1. Requires via. The first sub-flow is brought up and allowed to complete the key exchange before the rest, which are then created together. Above 8 the sockets are created in groups of 8 with brief pauses; above 32 a warning is logged because a rare kernel-level stuck-socket problem was observed at very high counts.
losslimit PERCENT
Loss threshold, e.g. 5% (the % is optional), default 100% (never). When the monitor's peer-reported loss exceeds it the link is marked lossy and removed from scheduling until it has been clean for proberecover. Needs monitor.
rttlimit DURATION
Mark the link late and stop using it while its RTT is above this (e.g. 250ms). It rejoins automatically when RTT recovers. Default off. Unlike loss, this is judged per sub-flow.
mtu SIZE
Fixed UDP payload size in bytes, 0–65535, default 1400 (set 0/omit for the default). Takes effect immediately. Advertised to the peer; a path with no own value follows the peer's.
monitor
Adds a dedicated health-probe sub-flow to the link (in addition to the data sub-flows). Requires via. It cannot be removed on a live path other than by taking the link down and recreating it.
probeinterval DURATION
Time between probes. Default 1s. Shorter = faster failure detection, slightly more traffic and noisier statistics.
probewindow N
Number of most-recent probes the loss percentage is computed over (1–600), default 60. With the default interval this is "the last minute". Time covered = probewindow × probeinterval.
proberecover DURATION
How long loss must stay under the limit before a degraded link is trusted again. Default 60s. Longer prevents flapping on unstable links.
beat DURATION
Interval of the internal control exchange on data paths (RTT, rate and counter updates). Default 100ms; there is rarely a reason to change it. Write the unit (100ms); a bare number is seconds.
watch
Only for status views: refresh every second.

6. Serving many clients (multi-client mode)

A normal tunnel joins exactly two machines. Multi-client mode lets one server serve any number of clients (up to 128) on a single UDP port and a single tunnel interface, with every client completely independent of the others. It is started with bind … hub and managed with the peer command. Ordinary clients are used unchanged: a client does not know or care whether its server is a plain or a multi-client one.

Terminology

In this chapter a client (the command line calls it a peer) is one remote machine with its own key and its own set of settings. The server keeps one fully separate session for each.

6.1 What is isolated per client

Per client (never shared)Shared by all clients
Pre-shared key, session keys and key rotationThe UDP port and its sockets
All of its paths, sub-flows and health monitoringThe worker threads
Rate limits in both directions, and the shaping queueThe tunnel interface (vx0)
MTU, pref, loss and RTT limits, maximum pathsThe operating system's routing table
kxtimeout, timetolerance, keepalive, reorderwindow, strictorder
The inner IP addresses it may use
Error and drop counters

The practical meaning: changing, limiting, restarting, overloading or removing one client never changes what any other client experiences, and a client cannot read, spoof or disturb another's traffic.

6.2 Quick start: one server, two clients

1. Give every client its own key (never share a key between clients — the server uses the key to tell clients apart, and refuses a key that is already in use):

$ vortex keygen > key-alice; vortex keygen > key-bob
$ chmod 600 key-alice key-bob
# copy key-alice to alice's machine and key-bob to bob's machine, securely

2. Start the server in multi-client mode (note: no keyfile):

# vortex bind dev vx0 hub from addr 0.0.0.0 port 5000

# ip link set vx0 up

3. Register the clients. Each gets the inner address(es) it owns, and optionally its own limits:

6.5 MTU in multi-client mode

A tunnel interface has one MTU, but clients may have different path MTUs. Instead of lowering the interface MTU to the smallest client (which would make one client's setting hurt everyone), the server:

  • sets the interface MTU to the largest client's (or the bind mtu you pinned);
  • for a packet too large for the one client it is addressed to, drops it and returns a standard ICMP Fragmentation needed (IPv4) or Packet too big (IPv6) message, so the sender shrinks its packets for that destination only.
# vortex peer set alice mtu 1200
$ ping -M do -s 1300 10.77.0.2      # 1328-byte packet, to alice
From 10.77.0.2 icmp_seq=1 Frag needed and DF set (mtu = 1178)
$ ping -M do -s 1300 10.77.0.3      # the same packet, to bob
64 bytes from 10.77.0.3: icmp_seq=1 ttl=64 time=0.5 ms

6.6 Routing, forwarding and clients talking to each other

  • Give the server's tunnel interface an address in the clients' network (10.77.0.1/24) and each client an address in it (10.77.0.2/24), as in the quick start. The allowed prefixes must be exactly the addresses the client uses as its source.
  • Packets from the server for an address no client owns are dropped and counted as no-route. Packets from a client with a source address it does not own are dropped and counted as spoofed for that client. Harmless IPv6 link-local and 0.0.0.0 sources are dropped without being counted.
  • Internet access for clients: enable IP forwarding and NAT on the server, as in the quick start; clients use the server's address as their gateway.
  • Client-to-client traffic is not forwarded unless you allow it: the packet arrives at the server's interface and the operating system forwards it back out (sysctl net.ipv4.ip_forward=1, and net.ipv6.conf.all.forwarding=1 for IPv6). Also run sysctl net.ipv4.conf.all.send_redirects=0, otherwise the server answers with ICMP redirects that clients on the same subnet do not need. Use a firewall rule on vx0 to forbid it if you want clients isolated from each other.
  • If several clients live on one machine (as in a test lab), each of its tunnel interfaces needs its own source-based route, otherwise replies leave through the wrong tunnel and are (correctly) dropped as spoofed.

6.7 Operating a multi-client server

  • Capacity: up to 128 clients, 16 prefixes each. Removing a client frees its name for re-use but not its slot, so a server that has added 128 different names must be restarted to add more.
  • Resources: a session is mostly unused memory. In testing, 20 connected clients used about 15 MB and ~3% of one core when idle. Throughput is shared by the same worker threads as in a normal tunnel (workers, cpus).
  • Roaming: a client whose address changes (a mobile connection reconnecting, a new NAT port) is recognised again by its key within a beat or two.
  • Unknown senders: traffic that is not valid for any client is dropped without any reply (a scanner learns nothing). Identifying a new sender costs the server a little work, so at most 2000 attempts per second are made; beyond that they are dropped and counted in rate-limited-lookups.
  • Revoking a client: peer del NAME, then remove its line from the peers file. To change a client's key, delete it and add it again with the new key file, then give the client the new key.
  • Persistence: as for a normal tunnel, nothing is saved. The peers file plus a start-up script (or the systemd unit below) is the way to make a configuration permanent.

The ordinary vortex@.service template expects a single keyfile, so multi-client servers use their own template, vortex-hub@.service (installed with the other systemd files):

DEV=vx-office

BIND_PORT=5000
OPTIONS=
alice key /etc/vortex/office/key-alice allowed 10.77.0.2/32

Two things the unit needs from you

Key files must be readable by root and by nobody else (chown root:root, mode 600): the service keeps only the CAP_NET_ADMIN capability, so it cannot read a key owned by another user. post.sh starts the moment the process does, before the interface necessarily exists, so begin it by waiting for it:

until ip link show vx-office >/dev/null 2>&1; do sleep 0.2; done
ip addr add 10.77.0.1/24 dev vx-office
ip link set vx-office up

6.9 Troubleshooting multi-client servers

A client connects but cannot reach anything
  • vortex peer list — is the client listed, with PATHS > 0?
  • Does the client's source address match allowed? A growing spoof count means no.
  • no-route growing in vortex show means the server is sending to an address no client owns.
  • Does the client use its own key? A client with another client's key will be recognised as that client.
A client's speed is below its limit

Download (tx) and upload (rx) limits are enforced exactly and typically allow 94–96% of the configured value as TCP goodput (headers and tunnel overhead count against it). Values below that point to the client's own link or its own rate setting. Look at the DROPPED column: steadily growing tx or rx means the client is pushing beyond its limit, which is working as intended.

peer add says "Address already in use" / "Key was rejected by service" / "File exists"

Another client already owns that prefix, uses that key, or has that name. Each must be unique. Use peer list to see who.

Two clients on the same subnet cannot reach each other

Enable forwarding on the server and switch off ICMP redirects (see 6.6), and check no firewall rule blocks vx0 to vx0.

The defaults are safe. The table below summarises when to deviate.

6.2 Rates (tx / rx)

  1. Measure each link's real speed in each direction (e.g. with a speed test or iperf3) without the tunnel.
  2. Set tx to about 90–95% of the link's upload and rx to 90–95% of its download, on the machine where the link is physically attached.
  3. If the link is split into N sub-flows, divide those numbers by N (rates apply per sub-flow).
  4. The server inherits the matching limits from the client's advertisements; you normally configure rates only on the client.
  5. Use auto only if link speeds vary a lot and you are comfortable with experimental behaviour; give it a tx cap as an upper bound.

Rates too high cause queueing and loss at the ISP; too low waste bandwidth. When in doubt, start at 90% and raise it until latency under load begins to rise.

6.3 Number of sub-flows (connections)

  • 1 is right for most low-latency links.
  • 4–8 is a good start for high-bandwidth or 50–150 ms links. Increase gradually while watching vortex path watch and your real throughput.
  • More than 16–32 rarely helps and each sub-flow adds work. Above 32 a warning is logged.
  • Pick a multiple of your worker count so work divides evenly (e.g. 4 workers: 4, 8, 12, 16 sub-flows).

6.4 Workers, CPUs and queue length

  • The default (cores − 1) leaves one core for the rest of the system and is a good starting point.
  • On a router that also does heavy forwarding, use cpus to keep vortex on specific cores, or lower workers.
  • If one worker is at 100% and others idle, you probably have too few sub-flows/flows to spread: raise connections.
  • Raise qlen only if you see transmit-queue drops on the TUN device during bursts; larger queues add latency.

6.5 Health thresholds

GoalSuggested
Fast failover (seconds)probeinterval 500ms probewindow 20 proberecover 20s losslimit 10% — reacts quickly; more false alarms on noisy links.
Stable, rarely flapping (default)probeinterval 1s probewindow 60 proberecover 60s losslimit 5%
Very unreliable link (mobile)losslimit 10%, proberecover 120s to keep a flaky link out until it is clearly steady.

Remember: loss % is computed over probewindow probes, so the smallest non-zero value is 1/probewindow. With a window of 20, one lost probe is already 5%.

6.6 Reorder window

  1. Set both ends the same way, because each direction is resequenced by its receiver: vortex set dev vx0 reorderwindow 100ms. strictorder is on by default, so every packet, TCP included, is numbered and released in exact order.
  2. With strict order the window is only a cap on how long a really missing packet is waited for; in-order packets are never delayed. A value of 100ms is a safe starting point. The actual wait is usually just the delay difference between the links plus about 3 ms. Measure that difference with vortex path (the slowest minus the fastest RTT, divided by two).
  3. Test a single-stream transfer (iperf3 -c ... -P 1), watch the retransmit column, and compare strictorder on with strictorder off. In lab tests with two jittery links, one TCP stream went from roughly 500–600 to 800 Mbit/s and the number of out-of-order events fell by about 20 times.
  4. If one end runs an older build, nothing breaks, but the improvement only appears in directions where both ends run the new one.
  5. A genuinely lost packet delays what follows it by up to the window (normally a few ms). Turn it off with reorderwindow 0, or use strictorder off, if latency-sensitive traffic on a lossy link suffers.

6.7 MTU

  • Leave at 1400 unless you have a reason.
  • Increase to 1472 (IPv4) / 1452 (IPv6) only on clean 1500-byte Ethernet paths, for slightly better efficiency.
  • Decrease (1280–1350) if the path crosses other tunnels (VPN-in-VPN, some mobile networks) and large downloads stall while pings work.
  • Set the same value on both ends or on one end only; the unset side follows. All paths should agree: the tunnel MTU is the smallest one.

Tuning: UDP socket buffers (VPS and router)

Every UDP socket has a receive buffer. If packets arrive faster than the program can read them for a moment, the ones that do not fit are silently discarded by the kernel, and TCP inside the tunnel sees them as loss. The default buffer is small (about 208 KB, only 3–4 ms of data at 600 Mbit/s). Vortex does not request a bigger one itself, so on a busy or slow machine you can enlarge it with two system settings, without changing the program.

SettingWhat it doesNeeded for vortex?
net.core.rmem_defaultReceive buffer every new socket getsYes — this is the one that takes effect
net.core.wmem_defaultSend buffer every new socket getsYes
net.core.rmem_max, wmem_maxOnly the ceiling for what a program may ask forNot needed (vortex never asks); harmless to raise
Do you need this?

Check first. Run a slow test and compare the counter before and after: grep Udp: /proc/net/snmp and look at RcvbufErrors in the second line. If it does not grow, buffers are not your problem and you can skip this section (in lab tests it stayed at 0 even with a CPU-starved receiver). If it grows, apply the settings below on the machine that is receiving the slow direction — ideally on both machines.

1. Try it once (lost at reboot)

# sysctl -w net.core.rmem_default=4194304
# sysctl -w net.core.wmem_default=4194304
# sysctl -w net.core.rmem_max=8388608
# sysctl -w net.core.wmem_max=8388608

4194304 is 4 MB; the kernel stores about double, so the real buffer is around 8 MB. On a router with little memory use 2097152 (2 MB) instead. These settings apply to all new sockets on the machine, not only vortex's.

Then restart vortex. Only sockets created after the change get the new size; a running vortex keeps the old one.

2. Make it permanent: VPS (Debian / Ubuntu)

# cat > /etc/sysctl.d/90-vortex.conf <<'EOF'
net.core.rmem_default = 4194304
net.core.wmem_default = 4194304
net.core.rmem_max = 8388608
net.core.wmem_max = 8388608
EOF
# sysctl --system                      # applies it now and re-reads it on every boot
# systemctl restart vortex-hub@NAME    # or whichever vortex service/command you run

The system loads /etc/sysctl.d/*.conf early in every boot, before services such as vortex start, so after a reboot vortex's sockets are created with the large buffers automatically.

3. Make it permanent: OpenWrt router

# cat >> /etc/sysctl.conf <<'EOF'
net.core.rmem_default=2097152
net.core.wmem_default=2097152
net.core.rmem_max=4194304
net.core.wmem_max=4194304
EOF
# sysctl -p

OpenWrt applies /etc/sysctl.conf at boot. For a guarantee that does not depend on the order things start in, also put the same commands at the top of your own start-up script, before vortex bind, after the initial sleep:

#!/bin/bash
sleep 10

# larger UDP buffers: must come BEFORE vortex creates its sockets
sysctl -w net.core.rmem_default=2097152
sysctl -w net.core.wmem_default=2097152
sysctl -w net.core.rmem_max=4194304
sysctl -w net.core.wmem_max=4194304

vortex bind \
  dev vx1 \
  ...

Setting the same value twice is harmless, so doing both is safe. A line such as #sysctl -w net.core.rmem_max=... on its own (the old commented-out line) does nothing for vortex, even without the #.

EventAre the large buffers still used?

5. Check that it worked

# sysctl net.core.rmem_default                 # should print your value, not 212992
# ss -umen | grep -A1 vortex | head          # "rb" in skmem should be about double your value (if ss is installed)

Larger buffers absorb short bursts; they cannot make a slow CPU or a lossy link faster, and if the receiver stays overloaded for long they only add delay. If throughput is still low with RcvbufErrors at 0, look at link loss (vortex path watch, losslimit) and the worker count instead.

7.2 Bond two internet lines (fibre + DSL) for more throughput

Fibre: 200 Mbit down / 100 up. DSL: 50 down / 10 up. Both main links, so same preference.

# vortex path up via eth0 dev vx0 monitor connections 4 losslimit 5% \
      rate fixed tx 22mbit rx 45mbit            # per sub-flow: 90 up / 180 down in total
# vortex path up via ppp0 dev vx0 monitor connections 2 losslimit 5% \
      rate fixed tx 4mbit rx 22mbit             # per sub-flow: 8 up / 44 down in total
# vortex set dev vx0 reorderwindow 100ms       # if single TCP streams underperform (set it on both ends)

Expected: roughly 230 Mbit/s down and 98 Mbit/s up in aggregate, shared in proportion to the configured rates.

7.3 Primary link with automatic LTE backup

# vortex path up via eth0  dev vx0 monitor losslimit 5% rate fixed tx 90mbit rx 180mbit pref 0
# vortex path up via wwan0 dev vx0 monitor losslimit 10% rate fixed tx 15mbit rx 40mbit pref 1

With both healthy, wwan0 shows ready and carries only probes. If eth0 becomes lossy, degraded or disappears, wwan0 takes over; when eth0 has been clean for proberecover traffic moves back. Because the path follows the interface name, an LTE modem that reconnects with a different IP resumes without any action.

7.4 Long, high-latency link

# vortex path up via eth0 dev vx0 monitor connections 16 rate fixed tx 6mbit rx 12mbit
# vortex set dev vx0 reorderwindow 20ms

16 sub-flows × 6 Mbit = ~96 Mbit/s up. Raise connections until throughput stops improving.

7.5 IPv6

# vortex bind dev vx0 keyfile /etc/vortex/key from addr :: port 5000
# vortex bind dev vx0 keyfile /etc/vortex/key from addr :: port 0 to addr 2001:db8::10 port 5000
# vortex path up via eth0 dev vx0 monitor

The remote address family decides whether an IPv4 or IPv6 address of eth0 is used. The inner (tunnelled) traffic can be IPv4, IPv6 or both regardless of the outer family.

7.6 Two tunnels on one machine

Give each a different dev and local UDP port, and always add dev NAME to management commands:

# vortex bind dev vx0 keyfile /etc/vortex/a.key from addr 0.0.0.0 port 5000 &

11. Troubleshooting

Management commands say "no active tunnel"
  • Is bind running? pgrep -a vortex
  • Run the commands as the same user. A tunnel started as root is invisible to a normal user: use sudo.
  • Look for the socket: ls /run/user/0/vortex /run/vortex.0 /tmp/vortex.0.
Path stays in probing / ping through the tunnel fails
  • Is UDP port 5000 (or yours) open on the server's firewall and cloud security group?
  • Does the client's to address/port match the server's from? vortex show on both.
  • Are the keys identical? sha256sum key on both machines. Then vortex show errors: a growing decrypt count points to a key mismatch.
  • Clock difference? date -u on both; show errors with clocksync confirms it.
  • Did you assign addresses and bring up vx0 on both sides? ip addr show vx0
  • Watch the traffic: tcpdump -ni eth0 udp port 5000 on the server. Nothing arriving means network/firewall; packets arriving but no replies means key/clock.
  • Multi-homed client: make sure packets for the chosen link really leave through it; policy routing and reverse-path filtering (rp_filter) on either end can drop asymmetric traffic.
Ping works but large transfers stall

Almost always an MTU problem on the underlying path. Test with a lower value: vortex path up via eth0 dev vx0 mtu 1300 monitor… (restate your other options), then verify with ping -M do -s 1250 10.77.0.1.

Throughput is far below the sum of the links
  • Packets dropped in the receive buffer? Compare RcvbufErrors in grep Udp: /proc/net/snmp before and after a test. If it grows, see Tuning: UDP socket buffers.
  • Are the rates correct? Too low tx/rx cap you. Check the configuration lines or path output.
  • Single stream vs many: try iperf3 -P 8. If many streams are fine and one is not, enable reorderwindow and/or add connections.
  • One CPU core at 100%? Add sub-flows or workers; check top -H.
  • Is a link lossy or late and thus excluded?
A link keeps flapping between running and lossy

Raise losslimit or proberecover, or lengthen probewindow, to be less sensitive. Check that rates are not set above what the link can truly carry: saturating a line causes real loss that the monitor correctly sees.

After restarting the client, one or more sub-flows stay at rtt 0

Re-issue the path up command (with the full set of options). Keep connections at or below 32; very high counts occasionally leave a sub-flow stuck because of a kernel-level socket anomaly, and the tunnel keeps running on the others.

The status shows probe-status no-monitor

No monitor sub-flow is configured on this link. Re-run path up via… monitor with your full option set. (Loss-based failover does not work without it.)

Log says "couldn't setup MTU" or "couldn't create tun device"

You lack privileges (CAP_NET_ADMIN/root) or /dev/net/tun is missing (modprobe tun; in containers add the device). A persistent device from an earlier run may belong to another user.

12. Security notes

  • Protect the key. It is the long-term secret. Store it with mode 0600 owned by root; share it only over a secure channel; rotate it (generate a new one, deploy to both ends, restart) if it may have leaked.
  • What is protected. All traffic, including control messages, is encrypted and authenticated. A packet is silently dropped (and counted) if it fails verification; the server does not answer strangers.
  • Forward secrecy. Session keys come from ephemeral Curve25519 exchanges and are replaced every kxtimeout.
  • Replay. The timestamp window limits replays to timetolerance. Keep it as small as your clock quality allows; use NTP.
  • Local access. The control socket directory is mode 0700, so only the same user (and root) can administer the tunnel. The control protocol is not an external API.
  • Privileges. Creating the TUN, changing the MTU and tracking interfaces need CAP_NET_ADMIN; the systemd unit grants only that.
  • Inner traffic is not filtered. Vortex checks only that inner packets are well-formed IP. Use your firewall (nftables/iptables) on vx0 to control what may pass.
  • Not anonymity. It protects confidentiality and integrity between two endpoints; the existence of the tunnel, its endpoints and packet sizes/timing are visible on the network.
